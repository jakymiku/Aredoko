**OpenCodeが作業中のため、現在の作業を中断・巻き戻しせず安全な区切りの後に次のUX縦切りとして扱う。** P0/P1等の進捗は最新コード・テスト・handoffを確認して引き継ぎ、今回の文書追記でリセットしない。本件は検索対象選択の実用改善であり、P5の全面デザイン刷新まで保留する必要はない。下のP0〜P5は全体計画として維持する。

## 現在の区切り（2026-10-15 続行）

P1の画像/表紙類似検索と登録フォルダハブはWindows確認済みを維持。**P0新baseline v7を事前凍結して実GPUで一度測定済み、改善試行累積1/2（対象のないcover検索のquery推論省略）を採用し、今回のP0を区切る。** [実測と失敗分析](search-phase-v7-results.md)。品質重み/閾値/routing変更は0件。残り枠を消費するための試行や既知fixtureの再調整はしない。次はP2の由来付きタグ候補・承認フロー。GPUの実行成功、人工入力の精度、実ライブラリ精度は分ける。

> P2基盤の現在：P2の最初の基盤として、由来付き候補の保存・承認/修正/却下・取消/再実行APIを追加。**実タグ生成adapter・WinUI承認画面・OCRは未接続**（既定生成503、契約検証は生成fixtureの偽adapter）。[実装境界とAPI](tag-suggestions.md)。P0 baseline済み・改善累積1/2は維持。

## 最優先の判断軸

Aredokoの存在理由は **「名前や保存場所を忘れたファイルを、曖昧な日本語・内容・見た目から短い手数で再発見する」** こと。同人誌/漫画だけでなく画像・制作素材・動画・音声/音楽も対象。単に機能数・テスト件数を増やすより、**正しい作品に到達できた割合、順位、所要時間、誤ヒット、索引コスト**を改善する。

2026-10-15時点で登録root、リスト/グリッド、タグ/棚/お気に入りの保存、ZIP/CBZ/画像ビューア、動画の範囲再生/seek、通常文字・関連語検索、文章/画像embeddingとモデルprofileは概ね存在する。動画/音声の**内容索引**、OCR・複数ページ文脈に基づく**自動シチュタグ**、**画像フォルダを一冊にする作品管理**は未完成または未実装。画像/表紙の右クリック類似検索は後続で実装・Windows確認済み。検索精度の一般化も未実証。

**直近は検索品質と内容理解へ開発の重心を移す。** 既存ビューア/動画プレイヤーの細かな装飾・一般的なプレイヤー機能の追加や全面的なGUI作り直しを優先しない。ただしデータ保全・重大バグ・退行・起動不能・検索フローのUX障害は先に修正してよい。

## フェーズ終了・次へ進むルール（反復ループ防止）

**P0は検索精度が完璧になるまで継続するフェーズではない。** 次の有限な作業枠で一区切りにする。

1. **P0 の1回限りの基本成果**: 新しい評価セットを事前固定し、既存検索モードのbaseline・失敗分析・改善候補を記録する。同じ評価データを名前だけ変えて作り直さない。
2. **P0 の改善試行は原則最大2件（セッションやAIの交代をまたぐ累積件数）**。各試行は仮説1つ→小さなコード変更→対象テスト→新規固定入力で効果比較。改善がなければ戻すか理由を記録し、次の仮説へ。改善案がない場合は0件で終了してよい。テスト失敗を「合格」とみなさず、安全性・基本機能の重大退行は先に修正する。
3. baselineと上記の試行枠を消化したら、**数値目標に未達でもP0を「今回の区切り完了・未解決課題はbacklog」として閉じ、P1の画像類似検索に進む**。同じ指標・同じfixtureを細かく調整し続けない。P0の再開はユーザーの新指示、明確な実運用の失敗、後続機能で見つかった新しい回帰など**新たな根拠がある場合のみ**。既知の課題だけを理由に自動的にP0へ戻らない。
4. P1以降は**各フェーズを小さい独立した縦切り（API→テスト→GUI、あるいはタグ候補→承認→OCR等）**に分ける。各縦切りは合格条件を満たせば先に進む。2回の修正・再検証でも外部環境・未承認モデル等で進めないなら、原因と未実装範囲をbacklogへ保存し、次に実行可能な別タスクへ進む。重大な既存機能の破損・安全問題は例外的に先に直す。
5. **再開ごとに進捗をリセットしない。** handoff冒頭へ「現在フェーズ／完了した縦切り／P0 baseline済みか／P0改善試行の累積回数（0〜2）／残課題／次の異なる実装タスク」を残す。過去に実行した評価や同じ修正を、新しいチャットだからという理由で再実行しない。
6. 成果が出たら機械的に順番を守る必要はない。**新しいユーザー指示・重大退行・明確な依存関係**は順序より優先する。ただしAI独自判断で同じP0改善サイクルを無限に延長しない。

## 実装順と受け入れ条件（優先度順）

### P0 — 検索品質の実測と改善ループ（最初に着手）

1. 既存 [search-quality-baseline.md](search-quality-baseline.md)、[search-quality-holdout.md](search-quality-holdout.md)、[literal-search-v6.md](literal-search-v6.md)、検索API/ランキングを確認。既存v1/v2/v6を結果に合わせて改ざんせず、新しい固定評価セットを**実行前に**確定する。
2. まず架空・生成した20〜50件程度の日本語質問と既知の正解作品/素材を用意する。「東方 巫女→（別名の）博麗霊夢の立ち絵」「純愛 学園もの 幼なじみ」「夕焼けの教室 背景」「白髪 赤い眼鏡」「正解が存在しない問い合わせ」等。ただし固有名詞の連想には事前の辞書/別名/確定タグが必要なことを区別する。実ライブラリ評価は**ユーザーの明示選択による小規模サンプルだけ**で、無断スキャンしない。
3. literal/関連語/text/cover/combinedを同じ対象・scopeで比較。Top1、Recall@5、MRR、Precision@5、正解なし時の挙動、検索時間、目的ファイルまでの操作回数を記録。metadata由来の正解と画像由来の正解を分ける。数字は入力セット・条件・件数と一緒に報告し、人工テスト100%を実ファイルの精度とみなさない。
4. 特に**文章と画像を混ぜると視覚クエリの順位が悪化する既知の事例**を評価する。単純なfusion重みの思いつき変更や「常に混合検索」を避け、明示モード・検索根拠・未索引fallbackを保持して小さな改善を検証。新しいholdoutで改善を示すまで自動ルーティングを既定で有効化しない。

**合格・一区切り条件:** 再現可能で凍結された評価入力、baseline/必要な改善前後の表、失敗例の分析、退行しない検索/フィルター/保存テストを残す。評価だけで終わらず、妥当な小修正が見つかれば実装まで進める。ただし**改善0件または最大2件でP0を一区切りとしてP1へ進む**。検索精度100%は移行条件にしない。

### P1 — 選択アイテムから「類似検索」（次の小さな縦切り）

1. 保存済みの**画像/表紙embedding**を再利用し、選択作品/素材の右クリック「似た画像・素材を探す」から候補一覧へつなぐ。まず画像で成立させ、動画/音声を処理可能と偽装しない。
2. API側で同じprofile/vector namespace/revisionの候補に限定し、選択元自身を除外、明示scope（登録root/種類/棚/除外）を厳守。未索引・古い索引・モデル未ロード・0件・取消・競合の動作を明示し、既存文字検索へ安全に戻れるようにする。
3. WinUI 3のネイティブなcontext menu、一覧/グリッド/詳細からの導線、検索結果への復帰、未保存draft保持、遅延応答排除を実装する。

**合格:** 生成した似た画像/異なる画像で候補と自己除外・scope・revision・説明を検証し、Windows実機で操作できたことと未検証項目を分けて記録。

### P2 — OCRと自動タグ、同人誌のシチュエーション理解

1. まず画像・表紙・漫画ページから**視覚タグ候補**を生成する交換可能なアダプタ、保存スキーマ（モデル/版・対象revision・根拠・候補/確定/却下）とWinUIの承認・修正フローを、小規模な生成素材で実装。
2. 次に日本語OCRを作品/ページ単位で索引に追加し、本文やセリフから検索できるかを評価。推論コスト、誤認識、読書ビューアとの照合を測る。
3. 「純愛」「学園もの」「幼なじみ」など人物関係・物語展開を要するタグは**複数ページのOCR/VLM/文脈集約**で候補提示する。表紙や単一コマだけで断定しない。「不明」を許し、根拠ページ・推定状態を保持。手動確定タグは再解析でも絶対に黙って上書きしない。
4. NSFWを含む実利用想定でも、モデルが扱える入力・拒否・誤判定を個別検証。モデル名や非検閲性だけで採用を決めない。取得・依存導入は事前の明示許可が必要。

**合格:** 自動タグを確定タグと区別したまま検索でき、承認/却下/手動編集・再索引・中断再開・根拠表示が保持される。実モデルの精度は別途小さな固定データで計測する。

### P3 — 画像フォルダを「一冊」、作品/ページを分離

画像フォルダ・ZIP・CBZをユーザーが**論理作品として扱うか単体素材として扱うか**明示的に選べる形へ。作品ID/元ファイル・ページID・revision/移動追跡/重複候補を分離する。ページ/セリフ/シーンへのヒットを作品に集約し、該当ページへ移動できるようにする。元ファイルは変更しない。既存の棚・手動タグ・読書位置を失わせない移行テストを必須とする。

### P4 — 動画・音声/音楽の内容索引

[media-content-plan.md](media-content-plan.md) に従う。既存の動画シーク/時間指定frame取得を再利用し、**時間付き代表フレーム→埋め込み→作品への検索結果集約→該当時刻へ移動**を最小の縦切りで実装。その後、EmbeddingGemma 2の正式な入力対応を検証し、音声認識（発話/歌詞）と音響・音楽特徴を目的に応じて区別して索引化する。無音WAVの名前タグ検索を音声内容理解の成功と呼ばない。profile/revision/前処理version/時間区間の根拠を保存する。

### P5 — 操作性・完成UI・大規模実用化

検索入力/履歴/フィルター/右詳細パネル/タグ承認の導線を先に改善し、その後 [design-vision-winui.md](design-vision-winui.md) に沿って**ネイティブWinUI 3**の洗練されたビジュアルライブラリへ段階的に移行。WebView/Electron/Tauriへの置換はしない。High DPI、High Contrast、Narrator、Tab順、狭幅、数万件/1TB、実ファイル・大きなZIP、CPU/RAM/VRAM・スクロール、配布/インストーラーは明示的な検証対象。配布完了や性能保証を現状から推測しない。

## エージェントの作業ルール

- **小さく実装→対象テスト→記録→次の小さな実装**。ロードマップの全項目を巨大な一括PRで作らない。現在のブランチ・HEAD・未コミット差分・既存PRを最初に確認し、既に実装済みのものは作り直さない。
- 優先順位は **P0→P1→P2** を基本とするが、**P0の有限な区切りと次フェーズへの移行を必須**とする。検索の重大な未完成/退行を残して動画プレイヤーの細部や見た目ばかり実装しない。P3/P4は基盤や評価の準備を小さく進めてもよい。複数のAIが並行作業している場合は直近HEAD/重複差分を確認。
- **製品ビジョンは維持、方式・モデルは交換可能。** 文字/手動タグ検索、scope、棚、お気に入り、既存ビューア、変更安全性を退行させない。検索スコアを「正解確率」と表示しない。
- 安全制約は [AGENTS.md](../AGENTS.md) と [product-vision.md](product-vision.md) を優先。元メディアへの書き込み・削除・リネーム・勝手な走査・外部アップロードは禁止。モデル/依存DL・OS変更は明示許可が必要。localhost API・認証境界を維持。
- **CIは原則実行しない。** AGENTSの月間節約/必要時のみ単発・反復禁止ポリシーを守る。ローカルで対象テスト、可能ならWindows Release/native GUIを検証。実施していない検証は「未検証」と書く。
- 作業先は従来の `feat/winui3-production-mvp-20261011` とDraft PR #5。mainへ勝手にmergeせず、過去のPR #6や試作PRを重複取り込みしない。作業完了ごとに [codex-handoff.md](codex-handoff.md) / [chat-handoff.md](chat-handoff.md) の先頭と既存PRを更新し、**結果・失敗・未検証・次の3手**を示す。

## 再開時の推奨最初の3手

1. **P2実adapterの最小接続**：[保存/承認API](tag-suggestions.md)を再実装せず、既存ローカルモデル資産と正式入力仕様を確認。実adapterはGPU排他/timeout/解放/取消を備え、固定した小規模素材で品質を別評価。新モデル/依存の取得は事前の明示許可が必要。
2. **WinUIの承認/修正/却下**：候補と確定・由来・根拠・stale/未接続/失敗を表示。draft/scope/検索/readerを保ちWindows実機の縦切りを確認。未承認候補を明示した検索は別扱いで追加する。
3. **OCR・複数ページ根拠**：ローカルOCRの仕様/費用を確認し、本文索引と根拠ページへ接続。表紙から関係性を断定しない。登録フォルダ保存scope/一括除外/キーボード、P3論理作品、P4時間付き動画/音声索引はbacklogに保持する。

これは**計画であり、新機能の実装報告ではない**。本書の方針が最新のユーザー指示と競合したら、その新指示を優先して文書を同期する。
