# Aredoko — プロダクトビジョンと開発原則

> **2026-10-17 ユーザー決定（実装の順序）**：まずEmbeddingGemma 2の直接画像・本文ページ検索を進める。OCR専用処理は、それでも内容の検索漏れが多いと確認されたときに実装を検討する。OCRは検索の必須工程にはしない。モデルを交換可能にする原則、既存の本文API/検索と手動整理機能は維持する。


> **この文書はAredokoの長期的な目的を定義する正本（single source of truth）。**
> 実装中の進捗報告や作業指示とは別物。Codex、Antigravity、ChatGPT、その他の開発エージェントは、機能や設計を提案・変更する前に本書を参照する。
>
> **ひとことで：** 名前を忘れても、内容や特徴を覚えていれば見つかる。Aredokoは、PCに保存した本・同人誌・画像・動画・音楽・素材を、曖昧な日本語から横断検索できるローカルメディア検索・整理アプリである。

## 1. 何を解決するソフトか

ローカルの膨大なファイルは、名前・場所・正確なタグを覚えていないと再発見しづらい。ユーザーが覚えているのは、むしろ作品の状況・内容・見た目・用途など断片的な特徴である。

Aredokoの中心体験は **Google検索のように短く曖昧なキーワードを入力し、事前に整理・解析・ベクトル化された手元のライブラリから、期待に近い作品・素材を見つけること**。

検索例：
- 「純愛 学園モノ 幼なじみ」→ 表記の違うタグ、説明、本文から関連作品を候補に出す
- 「白髪 赤い眼鏡 セーラー服」→ 画像・イラストの外見や特徴を探す
- 「夕焼けの教室 背景」→ 背景素材の視覚特徴や説明を探す
- 「前に保存した雨の街の画像」→ ファイル名を忘れても記憶の断片から探す

上の例は**目標とする検索体験**であり、現状すべて実装・精度検証済みという意味ではない。特に人物関係・物語上のシチュエーションは視覚特徴だけでは断定できない。

## 1.1. 原点となる「思い出せない→直接見つかる」体験

Aredokoは、以下のような**検索の遠回りを短縮できるか実証するソフト**でもある。

**既存の探し方：**

1. 「あれ、どこに置いたっけ？」とPCのファイルを探す。
2. それっぽい名前でWindows検索やEverythingを使っても見つからない。
3. 外部のGoogle検索で「東方 巫女」と検索し、「ああ、博麗霊夢だった！」と正しい名前を思い出す。
4. その正式名で改めて手元のファイルを探す。

**Aredokoが目指す探し方：**

1. 「あれ、どこだっけ？」
2. Aredokoに **「東方 巫女」** と入力。
3. PC内に保存済みの **博麗霊夢の立ち絵** が結果に出る。「そうそう、これこれ！」ですぐ目的の素材に到達できる。

利用者が**対象の正式名・ファイル名・保存フォルダを知らなくても、覚えている関連語・特徴・作品名・用途から見つけられること**が製品の核である。検索自体が目的ではなく「目的のファイルを発見するまでの手間」を減らす。

このケースは画像モデル単体の類似検索では不十分なことがある。「東方＋巫女」から関連キャラクター候補へつなぐには、**固有名詞、表記ゆれ、別名、作品・キャラクターの関連知識、タグ辞書、ユーザーが確定したメタデータ、意味検索**を補完的に組み合わせる。関連語の自動展開は候補提示であり、必ず一つの答えに決め打ちしない。手元にないファイルを存在するように見せず、曖昧な検索でもユーザーが正しい候補を選べるようにする。

**代表的な評価シナリオ：** ユーザーが選んだローカルの立ち絵素材（例：博麗霊夢）が、ファイル名に「東方」「巫女」が含まれなくても、事前のタグ付け・索引化後に「東方 巫女」という自然な検索で上位に見つかるか。ファイル名・タグの完全一致なしでの Recall@k / MRR、検索時間、発見までの操作回数を測定する。**これは目標であり、現在その精度が実証済みという意味ではない。**

## 2. 対象と製品としての位置づけ

- Windows向けのローカルファーストなメディアライブラリ・検索・整理アプリ。現在の製品GUIは **WinUI 3**。
- **同人誌・漫画・本**（画像フォルダ、ZIP、CBZ、必要に応じPDF）だけでなく、**画像、イラスト、背景・制作素材、動画、音楽**も主対象である。同人誌専用ツールにはしない。
- フォルダを明示登録し、複数ルート・大規模データ（数万件以上、1TB級）を想定する。元ファイルは動かさず、DB上でタグ・棚・お気に入りなどを管理する。
- 本のような複数ページの対象は **論理的な作品と構成ページを区別**する。ZIP/CBZだけでなく画像フォルダも「一冊」として扱える設計を目指す。単一画像などは素材として検索できる。
- Komga等との連携は任意。Aredokoの検索・整理は外部ビューワーやサービスの稼働に依存しない。

## 3. 検索の製品原則（最重要）

1. **検索入力は自然で曖昧でよい。** 正しいファイル名、厳密なタグ、完全一致の語を要求しない。日本語の省略、言い換え、複数語の組み合わせに対応する。
2. **ハイブリッド検索を目指す。** ファイル名・作者・タグ・説明・OCRの全文/部分一致、確定タグ、文章埋め込み、画像特徴ベクトルを組み合わせる。単一の埋め込みモデルにすべてを委ねない。
3. **ユーザーの明示フィルターを優先する。** 種類、登録ルート、棚、お気に入り等はAI推測で勝手に覆さない。意図推定やクエリ拡張は補助であり、失敗時は通常検索が使えること。
4. **検索結果は作品単位で理解しやすく示す。** ページや場面のヒットは根拠として参照可能にし、同一作品が過剰に結果を占有しないようにする。素材は個別ファイルで扱える。
5. **検索理由を説明できる構造にする。** タグ一致、文字一致、意味的類似、画像一致、対象ページなど、根拠と推定を区別する。類似度スコアを正解率・確率として表示しない。
6. **検索は軽快であること。** 原則として解析・埋め込み作成は登録後のバックグラウンドまたは明示的な索引ジョブで済ませ、日々の検索では作品全体を毎回VLM/OCRで読み直さない。
7. **精度は実測で判断する。** 想定質問と正解候補の固定評価セットを持ち、Recall@k、Precision@k、MRRなどと検索速度・索引コストを比較する。モデルの新しさではなくユーザーの検索成功を判断基準にする。

## 4. 自動解析・タグ付けの位置づけ

**自動タグ付けは最終目的ではなく、検索のために作品・素材の特徴を索引化する工程。**

- 画像の外見・構図・服装・背景などのタグ候補を軽量画像モデルで得る。
- 同人誌・漫画の「純愛」「学園もの」「幼なじみ」「催眠」「寝取られ」など、**文脈・関係性・展開に依存するシチュタグ**は、必要に応じた複数ページ解析、OCR、VLM、作品単位の集約によって判断する。表紙一枚や一コマの姿勢から確定しない。
- 解析対象・タグ辞書・関係性ラベルは、種類や用途に合わせて拡張可能にする。成人向けを含むライブラリについても、実際に扱えるか、拒否や誤判定がどの程度あるかをモデルごとに検証する。
- **手動確定タグ・取り込みタグ・AI推定タグを混同しない。** AIタグには候補、モデル/版、対象revision、根拠ページ、スコア、承認/却下状態などの由来を持たせる。ユーザーの修正を再解析で上書きしない。
- 検索には確定タグを高信頼の情報として使い、推定タグは強度と根拠に応じて補助的に使う。根拠不足なら「未判定」を許す。
- ユーザーによる修正履歴は、将来の辞書改善・分類器調整・追加学習・評価データに活用できる形にする。

## 5. 技術選定の原則

- **目標は固定、モデルは交換可能。** 現在のEmbeddingGemma 2は意味検索・マルチモーダル埋め込みの実装基盤であり、Aredokoそのものの定義ではない。
- WD系Tagger、OCR、Qwen系VLM、EmbeddingGemma派生、その他将来のモデルは **役割ごとに選択し、個別に評価**する。候補名は採用確定や精度保証ではない。
- 同時常駐を前提とせず、必要な推論ワーカーを順に起動・解放できるようにする。想定する開発機はWindows 11 / RTX 4070 Ti 12GB / RAM 32GB。GPU負荷、VRAM、索引時間、ゲーム等との共存に配慮する。
- 既存のPython＋SQLiteローカルAPI、WinUI 3、読み取り専用ファイルアクセス、モデルprofile・vector namespaceを可能な限り再利用する。
- ファイル単位のカタログ、論理的な作品単位、ページ/場面単位、検索インデックスを混ぜずに関連付ける。ファイルの改名・移動やモデル更新によって手動整理データが失われない設計を目指す。
- 解析の差分更新・中断/再開・進捗表示・対象範囲選択・キャッシュ管理を重視。AIが未設定でも文字/手動タグ検索や管理機能を使えること。

## 5.1. Windows版の将来の見た目（PoC後の目標）

**現状のWinUI 3 GUIは概念実証のためのシンプル・単色な仮置き**であり、最終デザインではない。検索・索引・タグ管理・読書・安定性などの主要機能が十分に整ってから、**「クリエイター向けの洗練されたダークUI」×「表紙・イラスト・制作素材が主役のビジュアルライブラリ」**へ段階的に進化させる。

Windows製品版は **WebViewを使わないネイティブWinUI 3** を維持。コンパクトな左ナビと検索欄、広いリスト/グリッド、右側のプレビュー・詳細・タグ編集パネルを基礎に、落ち着いたダークグレーと控えめな紫・青アクセント、Fluent 2らしいタイポグラフィ・角丸・アイコン・控えめな陰影や動きで完成度を高める。画像自体が映えること、見つけやすさ、操作性、メモリ/CPU負荷の低さを装飾より優先する。ライトテーマ、High Contrast、高DPI、キーボード操作にも配慮する。

**これは長期のデザイン到達目標であり、直ちにUIの全面改修を始める指示ではない。** Linux環境の開発エージェントは引き続き共通バックエンドを開発できる。将来他OSへ対応する場合は、既存バックエンドとAPIを活用して別の非WebViewフロントエンドを検討する。

具体的な画面像、パフォーマンス制約、Phase 1（PoC）→Phase 2（操作性）→Phase 3（ビジュアル完成）の順序は **[Windows版GUIデザイン方針](design-vision-winui.md)** を正とする。

## 6. 変えてはいけない前提

- **ユーザーの所有ファイルを勝手に変更しない。** 移動、削除、リネーム、上書き、変換、アーカイブ展開保存などは行わない。
- **明示登録・同意したルートだけを対象にする。** 私物・購入作品を開発テストに勝手に使わない。テストは生成データや明示的な小さなサンプルから始める。
- **ローカルファースト・プライバシー重視。** 作品画像や解析内容を無断で外部APIへ送らない。モデル取得等の外部通信も明示する。
- 既存の手動整理、棚、お気に入り、通常文字検索、素材検索、閲覧/プレビューを犠牲にしてAIだけを優先しない。
- インストール、モデルダウンロード、OS設定変更、破壊的git操作をユーザーの明示許可なしに実行しない。
- モデルの「動作した」と「正確に分類・検索できた」を混同しない。未実装・未測定・未検証はそのまま報告する。

## 7. 長期的な到達順序（固定の実装スケジュールではない）

1. **安全なライブラリと編集基盤**：明示登録、索引、一覧、検索、棚、タグ、お気に入り、元ファイルの保全。
2. **作品と素材を適切に区別**：本/ZIP/CBZ/画像フォルダの論理作品・ページ構造、単体素材の区別、閲覧基盤。
3. **ハイブリッド検索**：正確な文字/タグ検索と意味/画像検索を統合し、曖昧な日本語・複数語の検索を評価。
4. **自動内容索引**：視覚タグ、ページ/場面、OCR、文脈に基づくシチュタグを段階的に追加。AI提案を承認・修正可能にする。
5. **大規模化と品質改善**：差分索引、性能/資源管理、評価セット、ランキング改善、必要に応じた追加学習。
6. **周辺機能の拡張**：読書体験、Komgaなど任意連携、動画/音声の内容索引など。優先順位は現行の課題と検証結果で判断する。

## 7.1. 直近の開発優先順位（2026-10-15）

長期目標を実装へ落とすための**現在の優先順位と具体的な合格条件**は [開発ロードマップ](development-priorities.md) を参照。直近は検索品質の実測/改善、既存画像embeddingを利用した右クリック類似検索、OCR・レビュー可能な自動タグ候補・複数ページでのシチュエーション理解を優先する。画像フォルダの論理作品化と、時間区間つき動画・音声/音楽内容索引も継続目標。既存ビューア/一般動画再生の細部や全面的な見た目の刷新は、重大な欠陥を除き優先しない。評価セットでの検索成功と実運用の品質を混同せず、ビジョン・手動管理・プライバシー・WinUI 3ネイティブを守る。

## 7.2. 登録フォルダが増えても扱いやすい管理画面（2026-10-15 合意）

左ナビは「登録フォルダ」の入口へまとめ、メインビューのリスト／グリッドからフォルダ閲覧・複数選択検索・設定を行う。通常／AI／類似検索で選択範囲の意味を揃え、右詳細等から既存の初期棚・除外・スキャン・登録解除を編集する。初期棚はタグと区別し、個別の整理情報と元ファイルを保全する。一括編集は変更項目だけ保存。詳細と段階的な合格条件は [folder-library-management.md](folder-library-management.md)。これは合意済みの開発方針であり、今回の新画面実装報告ではない。進行中のOpenCode作業を安全に区切ってから着手する。
