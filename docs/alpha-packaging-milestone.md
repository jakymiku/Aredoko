# ALPHA-0: ダブルクリックで起動できる最初のアルファ版（2026-10-20 ユーザー指示）

> **現在の最優先マイルストーン。** AredokoをWindows上で普通のアプリとしてダブルクリック起動できる形にいったんまとめる。これは機能開発の終了・M1/M2/RC達成・公開配布の許可ではない。アルファが実際に動いたら **音声・音楽の内容解析／検索の実装、その後にUIの改善・最終デザイン** に必ず戻る。既存の引継ぎ、製品ビジョン、R01–R14台帳、既存機能、過去の試験記録は削除・改変しない。

## 狙いと完了ライン

* 既存アーキテクチャ（WinUI 3 + Pythonバックエンド + SQLite + AI）を維持する。単一巨大EXEへの圧縮は不要。最初は **1つの配布フォルダ／ZIPと、ダブルクリック起動できる Aredoko.exe またはインストール済みの標準ショートカット** でよい。通常利用者にターミナル操作、Python/dotnet SDK/winapp CLI、ソースチェックアウト、手動バックエンド起動を求めない。製品としてWindowsが要求するインストール操作は認める。
* 画像、ZIP/CBZ、フォルダ本、動画の既存機能（登録、明示索引、名前・タグ検索、既存AI検索、表示・閲覧、シーク、関連/類似検索、管理）を保つ。現在動いている音楽・音声の名前/タグ検索と再生も保つ。すでに実装した各機能をALPHA-0のために削ったり無効化しない。
* **音声・音楽の実ファイルからの自動解析／内容検索はALPHA-0完了の前提にしない。** 既存のR06–R09は未実装部分を未実装と明記し、ALPHA-0後の次工程に残す。現在の人工的な音響特徴や固定文字列による接続テストを「実音源解析が完成」と言わない。
* Python本体・バックエンド実行依存・必要なネイティブランタイムのパッケージ化、AI workerとモデルのパス解決を含む。許諾済みのローカルモデルを用いてAI機能が起動・索引・検索できるか確認する。再配布不可のモデルは無断同梱しない。新しい依存やモデルの取得/インストール等で既存ルール上承認が必要なら、該当作業のみ保留して許可を求める。AIあり配布とAIなし配布を混同しない。
* ユーザーデータ（SQLite、タグ、設定、索引、バックアップ、モデルキャッシュ）は更新で消えないよう、実行ファイル置き場とは分離する。既定の `%LOCALAPPDATA%\Aredoko` 等、既存の保存方針を尊重する。ユーザーの原本メディアに書き込まない。起動失敗時にログと復旧方法を示す。
* 既存起動時のPythonプロセスをアプリの起動・終了と適切に連動し、使用中のポート／多重起動／異常終了を扱う。初回と再起動後の起動を確認する。開発環境のないWindowsでの起動・主要機能・終了までを検証して初めて「ダブルクリックアルファ完成」とする。未確認なら「stagingのみ」等と正しく報告する。

## 次に担当するCodex / Antigravity / OpenCodeの手順

1. 現在の開発ブランチ `feat/winui3-production-mvp-20261011`、HEAD、git status、未コミット変更、Draft PR #5 を確認し、`AGENTS.md` → `docs/product-vision.md` → `docs/agent-start.md` → `docs/completion-roadmap.md` → 最新handoff/2026-10-20監査を読む。他エージェントが編集中の変更を上書きしない。PR #6や旧ブランチを誤って再取り込みしない。
2. **R13の現物から着手する。** `tools/package_release.py` はmanifestを出す staging-only で、Python/AIランタイム未同梱。現在の `tools/start-aredoko.ps1` は配布外Pythonへのfallbackがあり、`app/production_server.py` のAI workerは開発環境相対の `.venv-ai/Scripts/python.exe` を参照している。WinUIのWindows App SDK/packaged identity の起動条件も未検証。これらを実際のコードと照合し、完成扱いせず、動作する配布経路に直す。
3. self-contained .NET/WinUI、必要ならMSIX等の方式、Pythonの埋め込み／凍結方式と子プロセス、依存DLL、CUDA/CPU処理、相対パス、Windows App SDKのパッケージidentityを検証し、最小の実用的な配布方式を選択する。実行経路を `Aredoko.exe` または通常のアプリショートカットへ統一し、PowerShellウィンドウや開発用コマンドを利用者に露出させない。
4. 可能ならモデル再ダウンロードなしで既存の許可済み資産を使用する。モデル/依存のライセンス、必要容量、欠落時の案内、配布フォルダとユーザーデータの分離を明文化する。SQLiteの更新・バックアップ/復元パスも動作確認する。
5. **受入検証**：新規生成テストライブラリを使い、別のクリーンなWindows環境で「インストール/解凍 → ダブルクリック → バックエンド自動起動 → 画像/本/動画の登録・検索・閲覧、可能なAIの実推論 → 終了 → 再起動 → 保存状態維持 → 更新/削除後もユーザーデータ保持」を通す。GPU・配布ライセンス・実機GUI・Windows App SDK identity・起動条件など未検証の項目はそれぞれ別記する。クリーン環境がなければ完成と断言しない。
6. 本件の実作業は小さな検証可能なコミットで進め、変更したテストのみ必要に応じて実行。**CI/Actionsを自動連打しない、新依存・モデル取得/OS設定変更を無断実施しない、原本を走査/編集しない、mainへmergeしない、公開配布しない。** 過去のGUIテスト試行回数やR14 PARTIALを勝手にリセットしない。
7. 成果物の場所、起動方法、含まれる/含まれない機能、依存/モデル、検証済み範囲、残りのブロッカーを `docs/codex-handoff.md` / `docs/chat-handoff.md` とR13台帳に記録。**パッケージのスクリプトが走っただけでは完了にしない。**

## ALPHA-0が動いた後の開発再開（必須）

1. **音声・音楽の実入力対応に戻る。** R06のモデル・入力能力の実測と方式決定 → R07の録音/会話/発話の実抽出producer → R08の音響/曲調・類似検索producer → R09の既存GUIとの実データ動作検証。名前/タグ検索だけを「内容検索完了」と誤認しない。ユーザーが求める画像、動画、ZIP、音声、音楽の総合検索という製品ビジョンを維持する。
2. **UIを改良する。** 一旦使えるアルファで日常操作上の問題を把握し、既存のWinUI 3で、コンパクトな検索バー、広い結果一覧、右側詳細/タグ編集など製品ビジョンの完成形へ改善する。テスト用の文言を通常UIから除去し、通常ウィンドウサイズを優先。WebViewへ安易に移行しない。
3. 残るR11アクセシビリティ・DPI、R14実機受入、M1/M2/RCの各完了条件を追い、通常のベータ版や製品版を目指す。ALPHA-0はこれらの代替ではない。

## 判断原則

「まだ追加したい機能があるから配布を先延ばし」は避け、現在動く機能で最初のアルファを完成させる。逆に「配布スクリプトができたからすべて完成」も避ける。機能開発とUI改善は**後回しにするだけで、取りやめない**。既存の引継ぎ文書・評価証拠をすべて保持し、新規情報を追記する。
