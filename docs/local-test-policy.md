# ローカルGUI・GPUテストと失敗時の診断ルール（2026-10-24）

**現行の運用正本**。本ルールはAGENTS.mdから参照する。過去の「GUI 2/2・3/3 消費」「再試行禁止」「GUI/GPUに新許可が必要」は**過去の実測・失敗履歴**であって、他の実装や有意味な修正を翌日以降に試すことまで禁止しない。過去の生ログ、失敗と未受入の記録は削除・成功扱いしない。

## 通常テストは許可不要
- ローカルWindowsでの**WinUI GUI操作・スクリーンショット確認**、インストール済みの**既存モデルによるローカルGPU推論**は、新機能実装・バグ修正の関連検証として**事前確認なしで実施してよい**。小さい再現テストから始め、必要なLight/Dark・保存/再起動・VRAM解放まで関連範囲で確認する。実機が利用できなければCPU・静的・APIなど可能な関連確認を進め、GUI/GPUは未実施と記録する。
- **生成した独立fixture/DB/設定/出力先**を使用し、既存アプリやユーザーの通常DB、private folders、元メディア、モデル/プロフィール定義、インストール済みAlpha、ショートカットは無断変更しない。プロセスは所有PIDを把握して終了・解放する。GPUテストも長時間の大量処理を標準とせず、初手は小規模にする。
- **明示許可が従来どおり必要**：私物データの走査/改変・本番DB操作、未知の外部ダウンロード/モデルや依存の導入、外部送信、OS/ドライバ/セキュリティ設定変更、正式配布/更新、main merge。GitHub Actionsの自動/繰返し起動は不可（手動CIの従来ポリシーは維持）。

## 上限と詰まったときの脱出手順
1. **同じ原因を疑う同じテストの「変更なし再実行」は原則最大2回（最初の失敗を含む）**。新しい情報が得られないなら1回で止める。新しい名前・別runディレクトリ・セッション/エージェント変更だけで上限をリセットしてはならない。
2. FAILを確認したら、最初に**再現コマンド・HEAD・対象差分・fixture・期待/実際の結果・stack/log・スクリーンショット・所有プロセス**を採取し、**製品バグ／テストハーネス不具合／環境依存**を切り分ける。適当なsleep追加やテスト期待値の緩和だけで成功にしない。
3. **原因の仮説と実質的な修正（コード/fixture/環境条件の根拠ある変更）後に、変更した対象だけ再テスト**してよい。結果を読んで再度修正する。原則**有意味な修正→関連テストを2サイクル程度行っても同じ失敗・原因不明なら、追加実行より診断を優先**。
4. 診断は、最小再現への縮小、CPU/API/単体テストへの分解、失敗画面のUIA/フォーカス/イベント、GPUロード・OOM・VRAM/依存、直前の成功コミットとの差分を**関係する箇所だけ**調べる。新しい証拠・修正ができたら再度関連テストを実施してよい。試行上限を理由に根拠ある修正を永久にテストできなくするのは誤り。
5. まだ解決できないときは**FAILED/BLOCKED（未解決）**で、再現方法、ログ、試行回数と修正差分、原因候補、影響する機能、具体的な次の一手を短く残す。**「上限だからSKIP→別名で上限まで試す→またSKIP」の繰返しは禁止**。問題と独立した安全な開発は続行するが、未解決の障害をPASS/完了扱いにしない。
6. **原本・ユーザーデータ破損、復元/保存・認証・検索scope漏れ等の重大なFAILはリリースをブロック**。勝手に本番データを操作せず、危険な実装の差戻し・機能隔離などで封じ込める。実機/GPUが欠ける場合も「合格」と書かず、どの受入が残るか明示する。

## 旧上限を引き継ぐ場合
当時のGUI環境2/2、復元3/3、取得1/2、P3・棚などの結果は**再発調査に使う履歴**として保存。同じ失敗を別の日に無計画に再現し直さず、原因・コード変更の有無をまず確認する。一方、**新しい機能のテストや実質修正後の試験は通常どおり実行可能**。回数は「不具合ID/同じ仮説/変更前後」の単位で記録し、別名runを作って回数だけ復活させない。

**引き継ぎ書式**：対象とHEAD / PASS・FAIL・BLOCKED・UNRUN / 原因仮説と実修正 / 関連試行数 / ログ場所 / 次の一手。詳細な生ログをAGENTSやhandoffに貼り続けず、該当する技術文書・ログに残す。
