# Aredoko Windows版 — 将来のGUIデザイン方針

## 2026-10-22 本格UI開始条件と実装工程（最新）

[統合ロードマップ](polish-roadmap-20261022.md)のUI-0→UI-1→UI-2→UI-3を適用する。登録/検索/閲覧/保存/再起動が使え、主要な再生/60件境界/検索範囲/起動crash/data損失が解消した段階で主画面の本格開発を開始。すべての機能・細かなbug・実音声・配布・総合検証の終了を待たない。P3の仮想化と同時に左compact nav/中央検索とmedia一覧/右編集を完成形へ移し、P4–6の機能は共通UIで実装する。以下の「将来/機能が整ってから」はこの開始gateを意味し、開発延期の理由にはしない。WindowsはWinUI 3を維持、将来別native frontend向けのbackend/OS境界を保つが現在の移行/別UI実装は行わない。
## UIを複雑にしない・機能を減らさない（ユーザー指示、2026-10-16）

**本番のGUIは日常の検索・閲覧・整理に集中できる簡潔な構成にする。機能削減によって簡潔に見せてはならない。** AIエージェントのテスト都合で、検証用の長文・内部ID・実装説明・注意書きを通常画面へ追加し続けない。テスト手順/検証注記は文書・ログ、操作識別はAutomationIdに置く。

- 普段使う操作を前に出し、管理操作は名前付きツール、詳細条件やモデル版・前処理は説明/折りたたみへ整理する。既存機能・情報は到達可能なまま保持し、消去・恒久無効化・API撤去で代用しない。
- エラー、未保存、取消/進捗、元ファイル変更、未承認タグ、現在の検索範囲など、判断に必要な状態は常時分かる形にする。安全や検索範囲の警告を詳細の中へ隠さない。
- 長い技術説明より短い自然な日本語を使い、同じ説明やボタンを重複させない。必要な説明・根拠・モデル由来は任意に確認できる。新機能も既存の導線へ統合し、画面/設定を無制限に増やさない。
- 整理した操作へのマウス/キーボード導線、Light/Dark、狭幅、未保存編集、既存の検索/登録/読書/承認を検証する。AI用テストの古い見た目の期待に合わせて製品GUIを再び散らかさず、テストを新導線へ更新する。

> **位置づけ：将来のデザイン目標。2026-10-13時点のWinUI 3製品MVPは概念実証（PoC）であり、現状のシンプルな単色UIは仮置き。ここに書いた外観は実装済みを意味しない。**
> 本書は [プロダクトビジョン](product-vision.md) に従う。検索・管理・閲覧機能の安定性と検証が先、ビジュアルの全面刷新はそれらが整ってから段階的に行う。

## 将来のビジュアルコンセプト

**「クリエイター向けの洗練されたダークUI」×「表紙・イラスト・制作素材が主役のビジュアルライブラリ」**。

- Windows 11らしい **Fluent 2 / WinUI 3 のネイティブな操作感**を維持する。製品版Windows GUIはWinUI 3のまま。将来Linux/macOS用の別フロントエンドを加える余地は残すが、そのためにWebViewへ置き換えない。
- 落ち着いたチャコール〜ダークグレーを土台に、紫〜青系を控えめなアクセントとして用いる。必要に応じて明色テーマにも対応し、コントラスト・アクセシビリティを確保する。
- メディア画像そのものを主役にして、装飾の派手さで作品を邪魔しない。単色仮UIから脱するが、全面グラデーション、過剰な発光、常時動く装飾に頼らない。
- 角丸、余白、階層、タイポグラフィ、アイコン、選択状態、ホバー反応、繊細な陰影などで「完成されたアプリらしさ」を出す。Mica/Acrylic等は適所だけに使い、負荷と可読性を検証する。
- **WebView / Electron / TauriベースのUIへの置換は、現時点ではデザイン達成の手段にしない。** Webプロセス増加やメモリ使用量を避けたいというユーザー希望を尊重する。ただしネイティブだから性能や不具合が自動的に改善するわけではないので測定する。

## 目指す画面構成

1. **左：コンパクトなナビ**。ライブラリ種別、棚、お気に入りなどをアイコン＋短いラベルで整理。過度に画面幅を使わない。
2. **上：目立つが省スペースな検索バー**。曖昧な日本語、複数語、履歴、検索候補、タグ補完や絞り込みを将来的に扱う。通常文字検索は常に使える。
3. **中央：広く美しい一覧**。作品の表紙・素材サムネイルを大きく見せるグリッドと、高密度な詳細リストを切替可能に。大量件数でもスムーズなスクロール・仮想化・非同期サムネイル・軽い選択フィードバックを優先。
4. **右：作品詳細・編集パネル**。プレビュー、保存場所、手動タグ、AI提案タグと根拠、棚、評価などを分かりやすく配置。狭幅ではドロワー化。未保存変更やキーボードフォーカスの安全性を維持。
5. **検索結果の説明**。なぜヒットしたか（名前・確定タグ・関連語・意味・画像特徴・該当ページ等）を見せる。推定スコアを正答率に見せない。
6. **閲覧との往復**。漫画・同人誌は作品からページ、素材は個別画像へ自然に移り、検索結果へ戻れる導線を重視。見た目のために操作回数を増やさない。

## パフォーマンスと実装原則

- **見た目より検索・操作の応答性を優先。** 数万件規模、1TB級を想定し、画像は表示領域に応じて読み込み、適切にキャッシュ・破棄する。
- UIとPython/SQLiteの検索・索引・AIロジックは分離。WinUI側に独自の検索ロジックを持たせない。
- リソース辞書/デザイントークンに配色、角丸、余白、フォントサイズ、アイコン、状態を集約し、今後の段階的な変更・明暗テーマ・高DPIに対応できるようにする。
- アニメーションは短く控えめにし、Reduced Motion/システム設定と操作応答性を優先。大量画像スクロール中の装飾・高負荷エフェクトを避ける。
- キーボード、スクリーンリーダー、High Contrast、リサイズ、非同期選択切り替え、保存中のフォーカスを退行させない。
- Windows上での **Releaseビルド・実GUI操作・Light/Dark・狭幅/高DPI・メモリ/CPU/スクロールの評価**を段階的に実施。LinuxでXAMLを静的変更できてもWindows実機で動作確認済みとは主張しない。

## 段階的な導入

- **Phase 1（現在：PoC）**：検索・ライブラリ索引・読書・タグ編集等の機能、再現性、安全性、安定動作と精度評価が最優先。現在の簡素なGUIは仮置きとして許容する。
- **Phase 2（操作性）**：検索・グリッド/リスト・サムネイル・右編集パネル・ナビゲーションの導線と情報密度を整え、負荷とアクセシビリティを確認。
- **Phase 3（視覚品質）**：共通デザイントークンと画面コンポーネントを使って、ダークなクリエイターUI×ビジュアル主役のギャラリー表現を実装し、Windows実機で仕上げる。

これは期限付きの実装タスクではない。PoCを理由に将来のデザイン目標を忘れない一方、デザイン目標を理由に勝手な大規模UI作り直し、フレームワーク変更、モデル導入を始めない。実施時は小さな差分と目視・操作・性能検証で段階的に改善する。
