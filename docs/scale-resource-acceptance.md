# Aredoko 大規模受入・性能・資源予算検証記録 (R12 Scale & Resource Acceptance)

2026-10-19。コード確認基準：`feat/winui3-production-mvp-20261011`。
本受入は [docs/completion-roadmap.md](completion-roadmap.md) の R12（大規模受入と性能の終了条件）に基づき、登録50,001件メタデータおよび65,536件の保存ベクトルを用いて、列挙・登録差分・通常検索・CPUベクトル順位計算・カバレッジ・保留タグ・所有取消・停止時バックアップ復元・資源使用量・終了時間を網羅的に計測・検証した記録です。

> **境界条件に関する注意**:
> 「1TB対応」は単純なファイル数やベクトル数と等価ではないため、ファイル容量境界（512MiB）や再生時間上限（24時間・86,400,000ms）、CBZアーカイブ上限は別fixture・別契約で個別に検証し、「実1TBの私物走査済み」とは称しません。

## 1. 計測環境とパーセンタイル (p95) 算出定義

- **OS / プラットフォーム**: Windows 11 (x64)
- **Python ランタイム**: Python 3.11 / 3.14 (システム) および `.venv-ai` (CUDA_VISIBLE_DEVICES=-1, CPU計測)
- **テスト用データベース**: 一時ディレクトリ内に動的生成（Git管理外）
- **p95 算出公式**:
  最低10回以上のウォーム計測を実施し、順序統計量に基づく保守的な最近傍ランク方式（nearest-rank percentile）を採用：
  $$\text{p95} = \text{sorted}(L)[\lceil 0.95 \times |L| \rceil - 1]$$
  例: 10回計測時はソート後インデックス9（最大値）が厳格に p95 として採用されます。

## 3. 各項目の詳細測定記録

### 3.1 候補列挙と keyset streaming (50,001 件)
- 4つの独立 root（`root_0` 〜 `root_3`）に分散した50,001件のレコードを作成。
- `ai._iter_rows(scope=None, all_candidates=True)` により、メモリに全件を一括ロードすることなく、50,001件の ID を昇順に整列してストリーミング走査完了。所要時間: **1.069秒**。
- 最終ID 50,001（棚: `boundary-final`、タグ: `最後の検証候補`）の到達を確認。

### 3.2 通常文字検索 (Literal Search)
- クエリ: `最後の検証候補` (1件ヒット) および `大量受入検証` (50,001件ヒット)
- 1回の Cold 計測: 221.14ms
- 12回の Warm 計測: 平均 ~350ms、最大 387.47ms、**p95 = 0.3875秒**。
- 目標である p95 ≤ 1.0秒 を余裕を持って達成。

### 3.3 CPU 保存ベクトル順位計算 (65,536 ベクトル)
- EmbeddingGemma 768次元の単位正規化ベクトル 65,536件 を SQLite `ai_vectors` に格納（ファイルサイズ約205MiB）。
- `scores_with_content` により、Candidate IDs の 256件バッチ走査・BLOBデシリアライズ・有限性検証・内積計算を実施。
- Cold 実行: 9.646秒
- Warm 10回実行:
  - Run 1: 9.515s, Run 2: 9.512s, Run 3: 9.652s, Run 4: 9.495s, Run 5: 9.546s
  - Run 6: 9.589s, Run 7: 9.580s, Run 8: 9.674s, Run 9: 9.557s, Run 10: 9.672s
  - **p95 = 9.674秒**（目標 p95 ≤ 10.0秒 を達成）。
- 予算内に収まっており、無理な投機的最適化による浮動小数点精度や契約の破壊は不要であることを確認。

### 3.4 カバレッジと R01 契約の整合
- 登録全件 50,001 件に対し、`ai.coverage()` を実行。
- `candidate_total`: 50,001（ライブラリ全体の候補数）
- `target_total`: 10,000（`MAX_ITEMS=10,000` の安全上限で厳格に頭打ち）
- 所要時間: **2.312秒**。全件規模でもUIをブロックすることなく高速に応答。

### 3.5 所有検索取消の応答性
- `SearchRequests.prepare()` によりワンタイム32文字16進数の `request_id` を発行。
- `SearchRequests.cancel(request_id)` による中断受付レイテンシ: **0.1ms (0.0001秒)**。目標（≤ 1.0秒）を大幅に下回る即時応答を確認。

### 3.6 停止時バックアップと復元
- 50,001件のカタログDB（約16MiB）および65,536件のベクトルストア（約205MiB）のスナップショット作成時間: **3.12秒**。
- 新規復元先ディレクトリへのリストア時間: **2.48秒**。
- 復元後の SQLite `PRAGMA integrity_check`: `ok`。
- 50,001件のレコード数および各メディア情報が 100% 完全一致で保全されることを確認。

### 3.7 資源フットプリント (Footprint)
- **プロセス RSS メモリ**:
  - 初期常駐量: 29.37 MiB
  - 6.5万件ベクトル走査ピーク時: ~180-220 MiB（バッチ解放により肥大化なし）
- **ディスク容量**:
  - カタログDB (50,001件): 約 16.5 MiB
  - ベクトルストア (65,536件 768D float32): 約 205.8 MiB
- **WAL 単一ファイル整合性**:
  - `ai.close()` および `cat.close()` の呼び出し時に `PRAGMA wal_checkpoint(TRUNCATE)` が自動実行。
  - 終了後の `-wal` ファイルサイズ: **0 バイト**（メインDBに完全反映・単一ファイル整合性保証）。

## 4. 自動検証ハーネスの実行方法

本受入は以下のコマンドにより、いつでも決定論的に再現・検証可能です：

```powershell
# CPU受入ステージの実行（GPU/GUI不要、一時ファイル自動清掃）
python tools/test_scale_acceptance.py --stage cpu
```

実行結果は `data/acceptance/r12-scale-latest/scale-report.json` に構造化データとして保存されます。
